# UI 元素放置与布局一致性准则

> 适用范围：OMG-Draft-Seer 主窗口、Tier / Pairs / Draft / Build / Layout 页面以及浏览器和 Tauri 两种运行模式。
>
> 参考来源：cc-switch 的应用壳层与组件组合方式，以及当前 `page1`（Analysis / Screenshot）已形成的布局调整。借鉴的是工程和布局规律，不复用 cc-switch 的品牌、文案或图形资产。

## 1. 总体原则

### 1.1 先任务，后工具，最后状态

每个页面都按下面的阅读顺序组织：

1. 用户当前要完成的任务。
2. 完成任务所需的输入、筛选或操作。
3. 操作结果、统计信息和诊断状态。

不要把设置、说明或装饰放在主要任务之前。页面第一屏应该能回答“我现在在哪里”和“下一步做什么”。

### 1.2 页面是工作台，不是营销页面

应用使用场景是重复查看、确认和比较，因此采用紧凑、稳定、可扫描的工作台布局：

- 页面标题和主要内容靠左对齐，避免居中大标题。
- 使用明确的层级、边框和留白组织内容，不使用大面积装饰性图形。
- 一个区域只承担一个主要任务；不要把多个功能塞进同一个复合卡片。
- 页面区块使用整宽分隔线或无框布局；卡片只用于重复条目、弹层和确实需要边界的工具。

### 1.3 位置表达优先级

元素的位置必须表达优先级，而不是只追求对称：

- 左上：页面身份、任务标题、主内容入口。
- 主区域：截图、结果、表格或 Draft 中央池等核心对象。
- 核心对象旁边：直接作用于该对象的操作。
- 右上：页面级状态、辅助入口和独立窗口操作。
- 底部或次级区域：诊断、详细说明、低频配置。

## 2. 应用壳层

### 2.1 全局容器

- 主窗口使用单一纵向滚动流，内容从同一条左边界开始。
- 桌面端页面水平内边距为 `24px`；窄窗口降为 `16px`，不得让标题或控件贴边。
- 页面底部保留 `24px` 空间，避免最后一个结果贴住窗口边缘。
- 不为每个页面重复创建不同的外层宽度、外边距和顶部偏移。

### 2.2 顶部栏

顶部栏是全局层，只放全局信息和全局导航：

- 左侧放产品名称，设置入口紧跟产品名称。
- 右侧放一级页面导航；导航项使用图标时必须有 `aria-label` 和 tooltip。
- 顶部栏与页面内容之间使用一条底边框分隔，不使用额外大块背景。
- 品牌、设置和页面导航保持在同一水平线上；窄窗口允许换行或横向滚动，不压缩图标的可点击区域。
- 一级导航按钮保持固定尺寸，选中状态只改变背景、文字和阴影，不改变尺寸，避免导航抖动。

当前实现对应 `src/App.tsx` 的 app shell、header 和 `appPages`。后续新增一级页面时，只扩展同一导航模型，不在页面内部另造一套主导航。

### 2.3 页面标题区

除设置页外，每个页面都使用统一的标题结构：

```text
步骤 / 分类标识（eyebrow）
页面标题
补充说明、版本或数据范围                         页面图标 / 状态 / 页面级操作
```

- `eyebrow` 放在标题上方，用于说明流程位置或数据类别，不替代标题。
- 标题、说明和右侧信息在同一个标题区内；右侧内容不得漂移到下一个区块。
- 桌面端标题信息靠左、页面级状态靠右；窄窗口按“标题 -> 说明 -> 状态/操作”纵向排列。
- 标题区下方到筛选或主内容的间距固定为约 `18px`，不要每页自行发明间距。
- 页面之间切换时标题区高度和左边界保持一致，让用户依靠位置识别页面。

复用 `src/components/ui/PageHeader.tsx`。新页面只有在信息结构确实不同（例如设置页返回型标题）时才允许例外。

## 3. page1 的工作流布局

### 3.1 首屏顺序

Analysis 页的首屏固定遵循：

```text
顶部栏
  -> Screenshot 步骤标识
  -> 上传入口 / 当前截图
  -> 截图旁的直接操作
  -> 识别状态或错误
  -> 手动确认池
```

- 没有截图时，上传区域是主操作，使用整宽虚线框和明确的上传图标；不要同时显示一组抢占注意力的次要按钮。
- 有截图时，截图成为主对象，保持原始宽高比并占据可用主宽度。
- 替换截图、确认建议等操作必须放在截图附近，使用图标按钮并提供 tooltip；它们不应被移到页面底部。
- 错误和加载状态紧贴触发它们的对象，使用状态色和简短文本，不把状态单独做成大型弹窗。

### 3.2 Layout 页的双栏

Layout 是 Analysis 的同一工作流，不是另一套视觉语言：

- 宽窗口下，左侧为截图和校准对象，右侧为诊断信息或调试面板。
- 右栏使用固定的可读宽度（当前约 `520px`），左栏承担剩余空间。
- 窄窗口下先放截图，再放操作和诊断；两栏折叠为一列。
- 校准工具栏紧贴截图下方；加载、保存、重置和重新切片按“低风险 -> 高影响”排列，重置使用危险色并要求确认。
- 调试信息只在选中槽位后出现，不应在没有诊断需求时占据首屏。

### 3.3 手动确认池

手动确认池属于截图结果，不属于页面导航：

- 它放在截图和状态信息之后，保持与截图内容相同的主轴。
- 中央放能力，左右放英雄，顶部放终极技能，保持与源截图的空间关系。
- 每个槽位保持稳定的正方形尺寸；槽位编号固定在图标外侧，不参与图标缩放。
- 建议状态和已确认状态必须通过边框或状态色区分，但不能改变槽位尺寸。
- 窄窗口按“终极技能 -> 英雄/能力”纵向堆叠；固定格式的槽位网格可以横向滚动，但页面整体不应出现无意义的横向滚动。

## 4. 数据页面的放置规则

### 4.1 筛选工具栏

Tier、Pairs 和类似数据页统一使用“标题区 -> 筛选区 -> 数据区”：

- 分类 tabs 放在内容左侧，搜索放在右侧；窄窗口变为上下排列。
- 搜索框靠近结果区，不放在页面顶部全局导航内。
- 筛选状态必须保持在筛选控件本身，不用额外的说明卡重复展示。
- 过滤器、排序器等次要控件放在同一行；控件过多时换行，不缩小到难以点击。

### 4.2 列表、Tier 和表格

- 重复条目按统一的行高、图标尺寸和间距排列。
- Tier 行使用固定的等级列，内容从同一列开始；空状态也保留该列结构，避免切换筛选时页面跳动。
- 表格表头 sticky 时必须有不透明背景和更高层级，不能让内容穿透。
- 表格允许在自己的容器内横向滚动，不让整个应用壳层被宽表格撑开。
- 数值、排名、坐标、版本和 ID 使用等宽字体，并保持右对齐或列内对齐。
- 名称、说明等自然语言文本优先左对齐；不要用空格或手工字符模拟列布局。

### 4.3 Draft 页面

Draft 的视觉中心是中央能力池：

- 宽窗口采用“左队伍 -> 中央池 -> 右队伍”的三栏布局，中央区域尺寸稳定。
- 两侧队伍是上下文信息，不能抢占中央池的操作焦点。
- 播放、暂停、前后步和进度条紧贴中央池底部，形成一个连续的回放控制区。
- 窄窗口按“中央池 -> 左队伍 -> 右队伍”纵向排列，所有固定格式网格在内部约束尺寸。

## 5. 间距、尺寸与对齐

统一使用以下布局节奏。数值是默认值，只有固定格式内容或响应式约束需要时才例外：

| 场景           |               默认值 | 用法                         |
| -------------- | -------------------: | ---------------------------- |
| 页面水平内边距 | `24px` / 窄窗 `16px` | 主窗口两侧                   |
| 顶部栏内间距   |               `12px` | 品牌、设置和导航之间         |
| 页面区块间距   |               `20px` | 标题区、主内容、结果区之间   |
| 标题到控件     |               `18px` | 页面标题到搜索、上传或主对象 |
| 控件组间距     |                `8px` | 按钮、筛选器、状态项         |
| 面板内边距     |     `12px` 或 `16px` | 工具面板和结果面板           |
| 图标与文字     |       `6px` 至 `8px` | 按钮、列表项、状态           |
| 最小图标按钮   |               `32px` | 顶部导航和低频图标操作       |
| 常规按钮高度   |               `36px` | 带文字的主要操作             |

对齐规则：

- 内容、标题、筛选和结果共享同一左边界。
- 右侧状态和页面级操作共享同一右边界。
- 同一组控件的高度、图标尺寸和文字基线保持一致。
- 任何会被动态内容影响的网格、按钮、图标或计数器都要有稳定尺寸，避免 hover、加载和翻译切换造成位移。

## 6. 组件和交互规则

### 6.1 选择正确的控件

- 页面切换使用 tabs 或一级导航。
- 二值开关使用 toggle / checkbox，并明确显示当前状态。
- 选项数量有限且需要比较时使用 segmented control；选项较多时使用菜单或原生选择器。
- 数值范围使用 slider / stepper / input，不用一排文字按钮模拟数值输入。
- 不熟悉的图标必须有 tooltip；熟悉的图标操作也必须有可访问名称。
- 图标按钮只用于高频、明确的动作；关键任务的主要按钮保留文字。

### 6.2 按钮优先级

同一视觉区域最多有一个主按钮：

- 主操作：accent 背景，放在操作组的主要方向上。
- 次操作：中性边框或 raised surface。
- 辅助操作：ghost，仅在不需要强提示时使用。
- 破坏性操作：negative 色，靠近取消操作并通过确认对话框保护。

按钮文字应描述动作，例如“重新切片”“保存布局”；图标只补充识别，不替代必要的动作含义。

### 6.3 弹层、提示和状态

- Popover 锚定触发它的槽位、按钮或表格行，优先向下或向内展开，并避开窗口边缘。
- Dialog 用于确认不可逆或影响范围较大的操作；标题、说明和操作按钮按垂直顺序排列。
- Toast 只反馈已完成、失败或后台结果，不承载必须阅读的说明。
- 状态色只表达语义：accent 是当前焦点，positive 是确认/成功，warning 是需要注意，negative 是失败/危险。
- tooltip 用于补充信息，不要把关键流程藏在 tooltip 中。

### 6.4 层级建议

按下面的层级管理重叠元素，避免自行添加无规律的 `z-index`：

```text
普通内容
  -> sticky 表头 / 局部固定工具
  -> tooltip / popover
  -> dialog 遮罩与内容
  -> 原生 overlay 窗口
```

## 7. 响应式规则

- `600px` 左右是主内容从双栏折叠为单栏的边界；`700px` 左右用于 Draft 控件由横向变为纵向。
- 响应式变化优先改变排列方向、可用宽度和滚动容器，不随意缩小文字和可点击区域。
- 小窗口下，标题、说明、状态和按钮按阅读顺序排列；不要用 `justify-between` 把元素推到不可预测的位置。
- 固定格式内容（截图、槽位、表格、Draft 池）必须设定 `min-width`、比例或内部滚动边界。
- 翻译、长名称和错误信息都要在最窄支持宽度下验证；文本不能溢出按钮、卡片或相邻区块。
- 桌面端并排只是空间利用方式，不改变页面的语义顺序；移动端从上到下阅读仍应得到同样的任务流程。

## 8. 新页面验收清单

新增或重做页面时，逐项确认：

- [ ] 是否能在首屏看出页面身份、当前任务和下一步操作？
- [ ] 是否沿用了应用壳层、页面标题和左边界？
- [ ] 主内容是否先于筛选、说明和诊断出现？
- [ ] 直接作用于对象的按钮是否贴近对象？
- [ ] 是否只有一个明确的主操作，按钮优先级是否可辨？
- [ ] 图标按钮是否具备 tooltip、`title` 或 `aria-label`？
- [ ] 数据是否在自己的列表/表格容器中滚动，而不是撑开整个页面？
- [ ] 动态内容、长文本、中文/英文和窄窗口是否不会造成布局跳动或重叠？
- [ ] 是否使用了现有的 `PageHeader`、`Button`、`IconButton`、`Panel`、`Tabs`、`Toolbar`、`Field` 等组件，而不是重复实现相同语义？
- [ ] 是否同时检查了浏览器和 Tauri 窗口下的视觉顺序与交互层级？

## 9. 实现约束

- 颜色、圆角、阴影、字体和状态语义以 `src/styles.css` 的 token 为准。
- 通用控件优先放在 `src/components/ui/`，页面只组合控件，不复制一套变体。
- 页面级布局优先使用 Tailwind 工具类和现有断点；新增固定值必须能说明对应的内容约束。
- 所有间距、尺寸和断点的调整都要检查中文/英文、窄窗口、加载态、错误态和空态。
- UI 改动完成后至少运行 `npm run build` 和 `npm test`；涉及桌面窗口、overlay 或响应式行为时，再执行对应的 Tauri 验证。
